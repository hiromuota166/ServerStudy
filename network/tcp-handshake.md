# TCP の電話（ポート番号と 3ウェイハンドシェイク）

『マスタリングTCP/IP 入門編 第5版』の 6.2「ポート番号」と 6.4「TCP」（コネクション管理、再送タイムアウト）を読んで、自宅サーバーで `tcpdump` を使って確かめた記録。

## ひとことで言うと

TCP は、データを送る前に**電話のような確認**（SYN → SYN+ACK → ACK）をしてから話し始める。
相手がいなければ OS が **RST** で断り、ファイアウォールが捨てれば**返事がない**ので、送り直したあとタイムアウトする。

## 仕組み

### ポート番号（本の 6.2）

- **IP アドレス ＝ マンションの住所**、**ポート番号 ＝ 部屋番号**
- 待つ側は決まった部屋で待つ：ssh は `22`、nginx は `80`、uvicorn は `8000`（ただし `127.0.0.1` だけ）
- 送る側の部屋は、**毎回 OS が空いている大きい番号を適当に選ぶ**（エフェメラルポート）。返事はその部屋に届く。curl を2回打つと `38820` → `58718` のように変わる
- **PID とは別物**：PID は「**誰が**」（プログラムの番号）、ポートは「**どの部屋で**」。プログラムが部屋を借りる関係。`sudo ss -tlnp` で「どの部屋をどの PID が借りているか」が見られる

### 3ウェイハンドシェイク（本の 6.4 コネクション管理）

```
Windows（送る側）                  Ubuntu:80（待つ側）
  │── SYN       「もしもし、話せる？」 ──▶│
  │◀─ SYN+ACK   「聞こえる。そっちは？」 ─│
  │── ACK       「聞こえる」            ──▶│  ← ここで電話がつながる
  │── データ    GET / HTTP/1.1         ──▶│
  │◀─ データ    HTTP/1.1 200 OK        ──│
  │── FIN       「切るね」              ──▶│
  │◀─ FIN+ACK   「了解、こっちも切るね」─│
  │── ACK       「了解」                ──▶│
```

- **HTTP の本文は、3つの確認が終わった後**に流れる
- `ack` の数字は「ここまで受け取った、次はここからちょうだい」の印
- 本の図では切るときの矢印が4本のことがあるが、相手が「了解」と「こっちも切るね」を**1回にまとめて**送ると3本になる

### 断られる（RST）と、無視される（DROP）

| 状況 | 返事をするのは | tcpdump に見えるもの | curl の見え方 |
|---|---|---|---|
| 誰かが待っている | アプリ（nginx） | `S` → `S.` → `.` → データ → `F` | 成功 |
| 誰も待っていない部屋 | **カーネル（OS 本体）** | `S` → `R.` の2行だけ | **0ms で** `Could not connect to server` |
| ufw が捨てる | 誰も返事しない | `S` が 1秒・2秒・4秒…の間隔で繰り返すだけ | **タイムアウト** |

- **FIN と RST の違い**：FIN は**つながった電話を切る**ときの「切るね」。RST は**そもそもつながらない**ときの「その番号は使われていません」
- **再送タイムアウト**（本の 6.4 の「再送タイムアウトの決定」）：返事がないと、送る側は**あきらめずに送り直す**。間隔は 1秒 → 2秒 → 4秒…と倍になっていく。部屋番号も `seq` も同じなので、新しい電話ではなく「同じ電話のかけ直し」
- tcpdump は **ufw より手前**（ケーブルから入ってすぐの所）で見ているので、ufw が捨てた SYN も見える

## 自分の環境では

### tcpdump の行の読み方

```
15:02:18.317590 IP 192.168.100.1.62628 > 192.168.100.10.80: Flags [S], seq 2070658502, ... length 0
     時刻           送り主の IP.ポート  >  宛先の IP.ポート       矢印の種類            データの量
```

| Flags | 意味 |
|---|---|
| `[S]` | SYN（もしもし） |
| `[S.]` | SYN+ACK（`.` は ACK） |
| `[.]` | ACK だけ（受け取った） |
| `[P.]` | データを送っている（Push） |
| `[F.]` | FIN（切るね） |
| `[R.]` | RST（その番号は使われていません） |

### 試したこと

**1. Windows → Ubuntu の 80 番（Hello のページ）**：9行

```bash
sudo tcpdump -i eth0 -n 'tcp port 80'                 # Ubuntu
curl.exe -s -o NUL http://192.168.100.10/             # Windows
```

- 送り主は `192.168.100.1.62628`（NATSwitch 側の Windows と、OS が選んだ部屋）。8080 は**家の Wi-Fi から来た人用の入口**なので、Windows 自身が直接送るときは通らない
- `[S]` `[S.]` `[.]` → `[P.]` GET（78バイト）→ `[.]` → `[P.]` 200 OK（279バイト）→ `[F.]` `[F.]` `[.]`

**2. Ubuntu の中で、誰もいない 9999 番**：2行

```bash
sudo tcpdump -i lo -n 'tcp port 9999'
curl http://127.0.0.1:9999/
# curl: (7) Failed to connect to 127.0.0.1 port 9999 after 0 ms: Could not connect to server
```

`[S]` → `[R.]`。返事までの時間は 0.000014 秒。

**3. Windows → Ubuntu の 8000 番（ufw が閉じている）**：SYN だけが4行

```bash
sudo tcpdump -i eth0 -n 'tcp port 8000'                       # Ubuntu
curl.exe --max-time 10 http://192.168.100.10:8000/            # Windows
# curl: (28) Connection timed out after 10008 milliseconds
```

```
08:33:20.51  [S]
08:33:21.53  [S]   ← 1秒後
08:33:23.53  [S]   ← 2秒後
08:33:27.54  [S]   ← 4秒後（次は8秒後の予定だったが、curl が10秒で打ち切り）
```
